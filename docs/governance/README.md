# Governance

How this system is held to account: which frameworks it maps to, what "good enough to release" means, and where the evidence lives. The reasoning, and the options that were rejected, are in [ADR 0016](../decisions/0016-governance-and-release-gates.md).

## Frameworks

- **[NIST AI RMF 1.0](https://www.nist.gov/itl/ai-risk-management-framework)** and its **[Generative AI Profile (NIST AI 600-1)](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-generative-artificial-intelligence)** give the structure:
  - *Govern*: decisions and ownership (the ADRs)
  - *Map*: the data card and the risk register
  - *Measure*: the eval and the release gates
  - *Manage*: the release check, and monitoring after deployment
- **[OWASP Top 10 for LLM Applications, 2026](https://genai.owasp.org/resource/owasp-genai-llm-top-10-2026/)** is the security control list. The control matrix maps each control to the OWASP risk it addresses.
- **EU AI Act.** A Q&A demo over public documents is not a high-risk use. The duty that applies is Article 50 transparency: tell people they're interacting with an AI system. According to legal commentary, that has applied since 2 August 2026, and the 2026 Digital Omnibus did not delay it. The current disclaimer ("Not financial, legal, or flight-training advice") does **not** cover this on its own, so the live demo must add a plain "answers are generated by AI" notice. That's on the deployment checklist. Re-check the Official Journal text before relying on the details.

Framework versions were checked on 2026-11-09.

## The release gates in one paragraph

[`evals/gates.toml`](../../evals/gates.toml) holds 11 thresholds, set on 2026-11-09 before the gold set existed. They cover quality, safety, cost, latency, judge reliability and figure coverage. Every dev eval report shows a "Release gates" table as guidance. The **binding** evidence is the one-time held-out final run, plus the injection runs, the judge calibration and the database's figure coverage. `scripts/release_check.py` combines them and exits non-zero unless every gate passes. Missing evidence counts as "not measured", which blocks release just like a failure. Deployment will run this check and refuse to ship on a non-zero exit.

**Known limitation:** calibration grades don't record which judge model or configuration they were graded against. `release_check.py` will accept any calibration file, so the owner must make sure it comes from the same judge as the final run.

```bash
uv run python scripts/release_check.py --final evals/reports/<final>.json \
    --injection evals/reports/<direct>.json --injection evals/reports/<indirect>.json \
    --calibration <name>
```
